### 「请求」样例覆盖的错误码约定

`src/service/api/` 里 `fetchCustomBackendError(code, msg)` 触发后端返回指定错误码，用来复现前端的统一处理分支：

| 错误码 | 前端行为 |
|---|---|
| `8888` | 直接登出 |
| `7777` | 弹确认框后登出 |
| `9999` | 刷新 token |
| `2222` / `3333` | 重复错误合并（并发多条相同错误只提示一次） |

### 角色可见性：`meta.roles` 在动态路由模式下**不生效**

这是本仓库最容易误判的一点，实测链路如下（2026-09-19 核实）：

| 环节 | 事实 |
|---|---|
| 前端路由模式 | `VITE_AUTH_ROUTE_MODE=dynamic`（`.env`） |
| `initDynamicAuthRoute()` | 只做 `addAuthRoutes(routes)` —— **没有任何角色过滤** |
| `filterAuthRoutesByRoles()` | 函数确实存在（`src/store/modules/route/shared.ts`），但**只被 `initStaticAuthRoute()` 调用**，动态模式下走不到 |
| 后端 `RouteService.getUserRoutes()` | `menuManager.getMenuTree(PARENT_LONG_0, true, null)` —— 第三个参数是 `MenuType`（客户端类型），**不是角色**；`getMenusByParentId` 只按 `parentId` + `clientType` 过滤 |
| 后端 `RouteMetaVO` | 字段只有 `title / i18nKey / icon / orderNum / hideInMenu / keepAlive / constant / href / activeMenu / multiTab / fixedIndexInTab` —— **根本没有 `roles`**，所以 `meta.roles` 连传都传不到前端 |

**净效果：任何登录用户都能看到全部已启用菜单**，包括标注了 `R_SUPER` 的 `/function/super-page`。
`sys_menu.meta` 里的 `roles` 是**死字段**，保留它只是与既有行保持一致的书写习惯
（`docs/sys_menu_message_migration.sql` 的尾部注释也记录了同一结论）。

> ⚠️ 因此**不要**用 `meta.roles` 来实现"某菜单只给某角色看"。当前若需要按角色控菜单，
> 只能靠后端在 `getUserRoutes()` 里真正按当前用户角色过滤菜单树（可参考 `sys_role_menu` 关联表）。
> 这是一个**尚未实现的缺口**，不是配置问题。

> ⚠️ 另注意：按钮级权限（`useAuth().hasAuth()` / `sys_operation`）是**另一套机制**，不受此影响。

## 二、异常页 `/exception`

菜单 ID `2075214528458522643`，`component: layout.base`，`order: 7`。

| 子菜单 | 路由 | `route_name` | `component` | 复用组件 |
|---|---|---|---|---|
| 403 | `/exception/403` | `exception_403` | `view.403` | `src/views/_builtin/403/index.vue` |
| 404 | `/exception/404` | `exception_404` | `view.404` | `src/views/_builtin/404/index.vue` |
| 500 | `/exception/500` | `exception_500` | `view.500` | `src/views/_builtin/500/index.vue` |

**演示的核心点：同一套 `_builtin/{403,404,500}/index.vue` 被两种路由复用。**

| 用法 | 路径 | 定义位置 | 特点 |
|---|---|---|---|
| **兜底常量路由** | `/403` `/404` `/500` | `src/router/elegant/routes.ts`（`layout.blank$view.403`） | `constant: true` + `hideInMenu: true`，不进侧边栏 |
| **菜单样例路由** | `/exception/403` 等 | **只在后端 `sys_menu`**，前端 `routes.ts` 无对应节点 | 走动态路由下发，`component` 写 `view.403` |

> ⚠️ 仓库里**没有 `src/views/exception/` 目录** —— `/exception/*` 完全靠后端菜单下发 + `src/router/elegant/imports.ts`
> 里的 `403/404/500` 键解析出组件。别去前端找这个目录。
>
> ⚠️ 那三条 `constant: true` 的兜底路由是否真的注册，取决于后端 `/sys/route/getConstantRoutes` 的返回；
> 历史上出现过该接口返回空列表、导致 403 兜底页不可达的问题（前端在空响应时不回退内置常量路由）。
> 改动路由守卫前请先确认这条链路。

## 三、多级菜单 `/multi-menu`

菜单 ID `2075214528458522647`，`component: layout.base`，`order: 8`。
**这是唯一一处验证 3 层以上侧边栏渲染的样例**，四层嵌套：

```
多级菜单              /multi-menu                              layout.base     (menu_level 1)
├── 菜单一            /multi-menu/first       component: NULL   (2)
│   └── 菜单一子菜单   /multi-menu/first/child  view.multi-menu_first_child        (3)
└── 菜单二            /multi-menu/second      component: NULL   (2)
    └── 菜单二子菜单   /multi-menu/second/child component: NULL  (3)
        └── 菜单二子菜单首页 /multi-menu/second/child/home  view.multi-menu_second_child_home (4)
```

**演示的核心点 —— 中间层 `component` 应写 `NULL`：**

- 顶层（一级）→ `layout.base`
- **中间层（二、三级）→ `NULL`**
- 叶子 → `view.{route_name}`

中间层填错会怎样 —— **后端现在会兜底清空，但仍应按约定写 `NULL`**：

| 中间层填什么 | 实际结果 |
|---|---|
| `NULL` ✅ | 正常（**约定写法**） |
| `layout.*` | 后端 `RouteService.buildRouteTree()` 里 `if (depth > 0) route.setComponent(null)` 会强制置空 → 正常。测试锁死：`should_clear_component_for_intermediate_menu` |
| `view.*` | 同上被置空 → 正常。测试锁死：`should_clear_view_component_for_intermediate_menu` |

也就是说，**写错在运行时不会出问题**（后端已加固），但这是"后端替配置兜底"，不是可以随便写：

- `docs/sys_menu_init.sql` 的审计管理注释（第 67 行附近）仍把它列为硬约束，理由写在 `RouteService.java:137-141`
  —— 中间层带 `layout.*` 会让前端再嵌套一层布局（内容区出现重复的侧边栏与标签栏），带 `view.*` 则因其内部没有 `<RouterView>` 导致子路由完全不渲染。
  这是**加固之前**的真实故障现象，注释保留下来是防止有人再把兜底去掉。
- 兜底只在"该节点有子节点"时生效；中间层若被误配成叶子（无子节点）就**不会**被清空。
- 依赖后端的兜底意味着：换实现、或某天兜底被回退，配错的菜单立刻炸。

> **结论：照抄样例写 `NULL`。** 别把"现在不会炸"当成"这么写没问题"。

这条约束已被 `docs/sys_menu_init.sql` 的审计管理段落（第 67 行附近）引用为权威依据，新增多级菜单时照抄本样例即可。

3. **写菜单行**：追加到 `docs/sys_menu_init.sql`（或单独的 `sys_menu_*_migration.sql`，可参照 `sys_menu_org_migration.sql` 的写法——**保住 ID**，因为 `sys_operation.menu_id` 引用它）
4. **在库里执行**该 SQL
5. **配文案**：`zh-cn.ts` + `en-us.ts` + `src/typings/app.d.ts` 三处的 `route.{route_name}`
6. **若新路径要经网关**：后端需显式新增网关路由（网关不会自动放行新前缀）

### `sys_menu.meta` 支持的字段

JSON 字符串，常见键：

| 键 | 说明 |
|---|---|
| `title` / `i18nKey` | 标题与国际化键（`i18nKey` 形如 `route.function_tab`） |
| `icon` / `order` | 图标与排序 |
| `roles` | ⚠️ **死字段**（动态路由模式下不生效，后端 `RouteMetaVO` 根本不接收）。别用它控可见性 |
| `hideInMenu` | 不在侧边栏显示（配合 `activeMenu` 使用） |
| `activeMenu` | 隐藏项的父级高亮目标（`route_name`） |
| `multiTab` | 允许多标签页并存（同时 DB 列 `multi_tab` 也要为 `TRUE`） |
| `keepAlive` | 页面缓存（同时 DB 列 `keep_alive` 也要为 `TRUE`） |
| `fixedIndexInTab` | 固定在标签栏的序号 |

> **DB 列与 meta 双写**：`hide_in_menu` / `keep_alive` / `constant` / `multi_tab` 在 PostgreSQL 里是 `BOOLEAN`，
> 必须写 `TRUE` / `FALSE`（不是 `1`/`0`），且与 `meta` JSON 里的同名键保持一致。
